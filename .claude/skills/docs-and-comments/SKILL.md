# コメントとドキュメントの規約

## 使い分け（この repo の決めごと）

| 置き場所 | 書き方 |
|---|---|
| コード内コメント / `docs/` / `README.md` | **いまどうなっているか**だけを書く。この版だけを読む人が読者 |
| `.claude/skills/` | **なぜそうなったか**を残す。過去に踏んだ罠と、その形にした理由 |

理由: `docs/` は配布物で、利用者にとって「前はこうだった」は雑音になる。
一方 Claude や次の開発者にとっては、同じ罠を避けるために経緯そのものが情報になる。
経緯を残したいときは `docs/` ではなくこちらへ書く。

## コメントに書かないこと

```
✗ 以前は setup フェーズのたびに再送していたため、〜という競合があった
✗ 〜で重複していたロジックを共通化した
✗ 従来どおり動く / 従来の挙動と変わらない
✗ 旧互換のエイリアス
✗ // const oldImpl = ... （コメントアウトしたまま残すコード）
✗ 実装をそのまま日本語に言い換えただけの行
```

書き換えるなら「なぜこの形なのか」を現在形で:

```
✓ サーバーが真実を持つ状態なので、クライアントに下書きを溜めない。
  溜めるとコントロール窓を複数開いたときに互いの古い値で上書きし合う。
```

## コメントに書くこと

- **不変条件** — 破ると壊れる約束。「必ず〜すること」「〜してはいけない」
- **非自明な理由** — なぜ素直な書き方をしていないのか
- **落とし穴** — 読んだだけでは気づけない副作用や順序依存

型で表現できるものはコメントにしない。判別共用体・述語・専用の型名で表せるなら、
そちらへ移す（`StageRules` を平坦な設定袋から共用体に変えたのがその例）。

## 形式

- ファイル冒頭は「何のファイルか」を1〜3行
- 関数の JSDoc は「何をするか」+ 非自明な制約があればそれだけ
- 強調は `**〜**` を使い、1つの説明に1つまで
- 日本語で書く（区切りコメントも含む）

## ドキュメント

- **機能を足しても章を末尾に積まない。** 同じ粒度のものは同じ場所に並べる。
  「後から足したもの」に見える構成にしない
- 「〜を追加した」「〜に変更した」ではなく「〜である」と書く
- ユーザーマニュアルは画面に出ている言葉を使う。実装の名前 (`armMatch` など) は出さない
- デベロッパーマニュアルはファイル名・関数名で書く。UI を変えたらファイル表も直す

## 変えたら追随するもの

UI の文言・構成を変えたときに直し忘れやすい場所:

- `docs/user-manual.md` の該当章（画面の名前・ボタン名・タブ名）
- `docs/developer-manual.md` §8 のコンポーネントツリー / §13-6 のファイル表
- `apps/electron/test-e2e.mjs`（文言で要素を探しているところ）
- `README.md` の「特徴」
